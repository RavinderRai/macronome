## Vision

### 10x Check (proposed during review)

What would make this a 10x portfolio piece for the freelance-CTO audience? The hypothesis tested in cherry-picks: lean on production-rigor signals (live eval surface, ADRs, OSS extracts) rather than additional app features. Conclusion after user push-back: code + telemetry + ADRs are the right portfolio surface for this audience and this scale (10–15 testers). Live dashboards and OSS extracts add operational complexity disproportionate to portfolio leverage at this scale.

### Landscape Insight (Layer 3 reasoning)

The AI macro tracker space is crowded with VLM-wrapper apps (Cal AI clones). What is underexploited: **operational maturity + interpretability + restaurant context**. Consumer apps deprioritize these because they don't move user growth metrics. For a portfolio targeting CTOs hiring freelance ML engineers, exactly the qualities consumer apps drop are the qualities that signal hireable seniority. The locked feature set (eval harness, dual deploy, distilled tagger, restaurant mode toggle, menu-photo flow, "why this recipe" interpretability chips, hidden dev dashboard) directly leans into this gap.

## Premise Confirmations

- **Domain choice (macro tracking) is right for the portfolio framing.** Crowded but the project leans into operational/interpretability angles consumer apps don't. Acceptable.
- **AI-only logging path is a deliberate UX bet.** Risk: hurts retention with testers who eat the same meals daily. Mitigated by the auto-saved 1-tap re-log.
- **Dual deployment is the unique hook.** The freelance CTO audience cares about pragmatic infrastructure thinking; this is a rare and recognizable signal.
- **Distilled LLM tagger over a classifier is the strongest portfolio choice.** Demonstrates modern fine-tuning workflows (LoRA, distillation, eval) — what 2026 ML engineers actually do.

## Inversion Reflex (what would make this fail as portfolio)

- **Half-shipped features.** A partially working photo→macros + a partially working menu photo + a partially built tagger reads worse than one finished thing. Discipline required: each ML stage hits eval + telemetry + writeup before moving to the next.
- **Drifting back into chasing user count.** This is not a startup. 10–15 engaged testers + measured eval numbers > 100 fly-by users + no metrics. Tester recruitment is distribution work, not engineering.
- **Custom-DAG NIH signal.** If the workflow framework stays custom without a well-justified ADR explaining why, it reads as "didn't know LangGraph existed." Either migrate to LangGraph (and write ADR-001 about the migration) or stay custom and write ADR-001 explaining the specific reason LangGraph couldn't meet a constraint. Don't leave the question implicit.
- **Cool features that aren't measured.** The personalization model and the distilled tagger only matter to a CTO if they have eval numbers. "I built X" without "X performs Y on metric Z" is anecdote, not evidence.
